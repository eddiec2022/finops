
# TASK 12 - Recommendations: RI/Savings Plan (Investigation + Build)

## Context
Tasks 9-11 covered the first three recommendation categories using custom heuristics
against data already ingested. This is the fourth and last category per GOV-001
Section 3.5: Reserved Instance / Savings Plan recommendations for steady-state
on-demand usage. Unlike the first three, Azure has a native API for this
(Microsoft.Consumption reservation recommendations) that could produce more accurate
savings numbers than another custom heuristic - but it's genuinely unknown whether
the current service principal's permissions (Reader + Cost Management Reader at
subscription scope, from Task 2) are sufficient to use it. Investigate before
committing to a design.

## Scope - Phase 1: Investigation (do this first, don't skip to building)

1. Attempt to call the Microsoft.Consumption reservation recommendations API
   (GET .../providers/Microsoft.Consumption/reservationRecommendations, or the
   current SDK equivalent in azure-mgmt-consumption if that's cleaner than raw
   REST) against the real subscription, using the existing service principal
   credentials already in .env
2. Record exactly what happens - a successful response (even if empty, which is
   plausible given this dev subscription's usage patterns), a permission/auth
   error (capture the exact error), or something else entirely
3. If it requires a role/permission the service principal doesn't currently have:
   STOP HERE. Don't request expanded permissions or add roles yourself - per
   CLAUDE.md, this is a security-relevant change and Edson's call to make
   explicitly, not something to work around. Report exactly what's missing
   (the specific role or permission name from the error) so a real decision can
   be made
4. If it works (even with an empty result): note whether the empty result is
   because the dev subscription genuinely has no steady-state usage pattern
   yet to recommend against (matches everything Tasks 9-11 already found about
   this environment's short history), not a bug

## Scope - Phase 2: Build (only if Phase 1 confirms API access works)

If and only if Phase 1 succeeds:

1. Endpoint - GET /api/v1/recommendations/reserved-instances
   - A live call to the Consumption API is a different pattern than the other
     three recommendation endpoints (which are pure DB reads) - that's fine
     and expected here, since this is Azure's own recommendation engine, not
     something to reimplement. Don't force this into the compute-on-read-
     from-DB pattern just for consistency with the others
2. Map the API's response into a consistent shape with the other three
   recommendation endpoints where it makes sense (resource/scope identified,
   a reason/basis, an estimated savings figure) - but don't force Azure's own
   fields to fit a shape they don't naturally have. If the response shape is
   meaningfully different, that's fine - explain the difference rather than
   mangling it to look uniform
3. Tests - mock the Consumption API client for the automated suite, same
   "no live credentials needed for pytest" principle as every other connector
   (Tasks 2/5/6). A live check against the real subscription is still the
   deliverable, same as always, on top of the mocked tests
