# TASK 4 - WSL2/Docker Restart: Root Cause Investigation (Round 3)

## Context
Task 3 confirmed the WSL2-instance-level restart cycling is NOT resolved - it is
active and ongoing, with irregular intervals from 1 second to 5+ minutes, still
occurring as of Task 3. Monitoring is in place and verified working
(ops/wsl-monitoring/), so recurrences are now logged, but root cause remains
unknown after two investigation passes that ruled out: Windows reboot, Hyper-V
VM-level restart, OOM-kill, Windows Update, Trusted Launch regression,
SystemSettings log correlation, and LxssManager issues.

Two new, specific leads to check this round, based on research matching this exact
symptom pattern:

## Scope

1. Check for a known Microsoft WSL networking bug
   - This setup matches a documented, currently-open WSL issue pattern: native
     Docker Engine inside a systemd-enabled Ubuntu WSL2 distro (no Docker Desktop)
     experiencing periodic WSL restarts, correlated with Hyper-V VmSwitch logging
     Event ID 285 (IOCTL_ENUM_NIC_COUNT_EX timeout) at the same moments.
   - Check the Microsoft-Windows-Hyper-V-VmSwitch-Operational event log for Event
     ID 285 entries, and check whether their timestamps line up with the restart
     timestamps already captured in /var/log/docker-restart-monitor.log
   - If it matches: this is a known upstream bug, not something fixable in this
     repo - report what mitigation options exist upstream rather than trying to
     patch around it blindly

2. Check for antivirus/EDR interference with the WSL2 virtual disk
   - Identify what endpoint protection is running on this VM (Windows Defender at
     minimum; check for additional EDR agents given this is a VAR/security
     environment)
   - Check current Defender exclusions (Get-MpPreference) for whether WSL2/Docker
     paths are already excluded
   - If not excluded: this is a strong candidate, since real-time scanning of the
     ext4 virtual disk while Docker has it mounted is a well-documented cause of
     exactly this unmount/remount cycling pattern
   - Do NOT apply any exclusions - this is read-only investigation. Report findings
     and the exact exclusion paths that would need adding. Disabling AV scanning on
     any path is a security posture decision Edson makes explicitly, not something
     to change silently as part of a diagnostic task

3. Cross-reference
   - Compare timestamps from both checks above against the monitor's log to see if
     either (or both) correlate consistently with actual restart events, rather
     than just confirming the log entries exist somewhere

## Explicitly out of scope for this task
- No new Azure feature work - still paused pending this
- No applying fixes automatically (AV exclusions, WSL version changes, etc.) - this
  task is diagnosis only; report findings and proposed fixes for Edson to approve,
  then a follow-up task applies whichever fix is confirmed

## Deliverable for review
- Whether Event ID 285 correlates with the restart timestamps (yes/no, with evidence)
- What AV/EDR is running, current exclusion status, and the exact paths that would
  need excluding if that turns out to be the fix
- A clear recommendation: which lead (if either) looks like the actual cause, based
  on correlation strength against the monitor log - not just "both are documented
  possibilities"

Same rule as before: if anything here is ambiguous, flag it rather than guessing.
