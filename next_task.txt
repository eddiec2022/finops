# TASK 9 - Recommendations: Rightsizing

## Context
Tasks 2/5/6/8 built inventory, utilization, cost, and forecasting. This starts
Section 3.5 (Recommendations) - the last major piece of Azure Phase 1. Rightsizing
comes first since it builds directly on utilization data that's already solid.
Idle/orphaned detection, non-peak scheduling, and RI/Savings Plan recommendations
are each separate follow-up tasks, not bundled into this one.

## Scope

1. Endpoint - GET /api/v1/recommendations/rightsizing
   - Compute-on-read, same philosophy as forecasting - nothing external to fetch,
     just deriving insight from utilization_metrics + resources already in the DB
   - For each VM and App Service in `resources`, compute average CPU utilization
     over the trailing `idle_lookback_days` window (reuse the existing setting
     from Task 5 - do not add a new one)
   - Flag resources where avg CPU < idle_cpu_threshold_percent (also from Task 5 -
     these settings exist for exactly this purpose, use them, do not hardcode)
   - For flagged VMs, suggest a smaller SKU using a simple heuristic (e.g. parse
     the SKU name's core-count component and suggest roughly half, staying within
     the same VM series/family). This is deliberately not a live Azure SKU
     availability lookup - that is real added complexity for a v1 advisory
     feature. State the heuristic's limitation plainly in the response (e.g. a
     `note` field) rather than presenting the suggested SKU as guaranteed available
   - For App Services, suggest a smaller tier using equivalent logic if a clean
     one exists; if App Service tier naming does not map as cleanly as VM sizes,
     it is fine to flag App Services as rightsizing candidates without a specific
     suggested tier rather than force a bad guess - explain whichever way you go
   - Resources with insufficient utilization history (less than the lookback
     window) should be excluded from results, not flagged based on partial data -
     same principle as the forecasting model's "insufficient data" handling in
     Task 7/8
   - Response: for each flagged resource - resource details, current SKU,
     suggested SKU (or explicit note if none), average CPU%, and an estimated
     monthly savings figure if calculable from the cost data already in
     cost_records (this will be approximate - say so, do not present it as precise)

2. Tests
   - Unit test the CPU-threshold flagging logic against fixture utilization data
     (clearly idle resource, clearly busy resource, insufficient-history resource)
   - Unit test the SKU-suggestion heuristic against a few real-looking SKU name
     patterns
   - Integration test the endpoint against seeded data

## Explicitly out of scope for this task
- Idle/orphaned resource detection (disks, IPs, stopped VMs, empty resource
  groups) - separate task next
- Non-peak scheduling, RI/Savings Plan recommendations - separate tasks
- Any UI/dashboard changes
- Persisting recommendations to a table - compute-on-read only for now, same as
  forecasting
