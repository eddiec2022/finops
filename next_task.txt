# TASK 11 - Recommendations: Non-Peak Scheduling

## Context
Tasks 9 and 10 covered rightsizing and idle/orphaned detection. This task adds the
third recommendation category per GOV-001 Section 3.5: identify likely non-production
resources with low overnight/weekend usage, and recommend a start/stop schedule as a
suggestion (not an automated action - v1 is advisory only). RI/Savings Plan
recommendations remain the last category, a separate task after this one.

## Scope

1. Endpoint - GET /api/v1/recommendations/non-peak-scheduling
   - Compute-on-read, same philosophy as the other recommendation endpoints

2. "Likely non-production" signal
   - GOV-001 says this can come from tags, naming convention, OR usage pattern -
     not all three required. Build at least: a tag-based check (common
     environment-indicating tag keys like "environment"/"env" with values like
     "dev"/"test"/"staging"/"sandbox" - check what's actually in the real
     synced resources' tags before hardcoding an exact tag key/value list) and
     a naming-convention check (resource name containing dev/test/staging/
     sandbox/demo, case-insensitive). Both are heuristics, not certainties -
     label results accordingly, same spirit as the SKU suggestion heuristic
     in Task 9
   - A resource can also qualify purely on usage pattern (see below) without
     matching either tag or naming heuristic - don't require all signals to
     agree, any one is sufficient per GOV-001's wording

3. Usage pattern analysis
   - For VMs and App Services, using the existing CPU utilization data:
     compute average CPU during "peak" hours (weekday, business hours) versus
     "off-peak" hours (nights and weekends), over the trailing
     idle_lookback_days window
   - This needs actual time-of-day/day-of-week bucketing of
     utilization_metrics.timestamp - a genuinely different kind of analysis
     than the flat-average approach evaluate_cpu_utilization uses for
     rightsizing. Build it as its own function, don't try to force-fit the
     existing one
   - Business hours definition is a real v1 simplification worth being
     explicit about: use a fixed weekday 8am-6pm UTC window rather than
     per-resource timezone detection (there's no reliable timezone signal in
     what's synced) - state this assumption plainly in the response, don't
     bury it
   - Flag a resource when off-peak usage is meaningfully lower than peak
     usage - pick a reasonable threshold (e.g. a ratio) and make it a
     configurable setting following the established pattern, not a hardcoded
     magic number
   - Resources with insufficient history for this analysis follow the same
     "exclude, don't guess" principle as every other recommendation endpoint
     so far

4. Recommended schedule
   - v1 doesn't need a fully custom per-resource schedule derived from the
     exact observed pattern - a standard template (e.g. "power off weeknights
     outside business hours, power off entirely on weekends") is a reasonable
     v1 scope. State it as a suggested starting point, not a precise
     optimization
   - Estimate monthly savings from the hours that would be powered off,
     using the same average-daily-cost-from-cost_records approach as the
     other two recommendation categories, scaled to the fraction of a
     week/month the schedule would have the resource off

5. Tests
   - Unit test the peak/off-peak bucketing logic against fixture timestamps
     spanning weekdays, weekends, and both sides of the business-hours
     boundary
   - Unit test the tag and naming heuristics
   - Integration test the endpoint against seeded data covering: a clear
     non-prod-by-tag candidate, a clear non-prod-by-name candidate, a
     production-tagged resource with an off-peak usage dip anyway (still
     qualifies, since usage pattern alone is sufficient), and a resource
     that's busy around the clock (should not be flagged)

## Explicitly out of scope for this task
- RI/Savings Plan recommendations - the last recommendation category, separate task
- Empty resource group detection - still deferred from Task 10, will be its own
  small task
- Any actual scheduling/automation - v1 is advisory only, this only ever returns
  a suggestion
- Per-resource custom schedule optimization beyond the standard template
