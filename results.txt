## Phase 1: Investigation findings (a deliverable on its own)

Wrote a small throwaway script (not committed - removed once its findings
were folded into the real connector code) that acquired an ARM token via the
existing `ClientSecretCredential` (same tenant/client/secret already in
`.env`) and called:

    GET https://management.azure.com/subscriptions/{subscription_id}
        /providers/Microsoft.Consumption/reservationRecommendations
        ?api-version={version}

against three API versions, to see what actually happens - not assumed from
documentation:

    api-version=2024-08-01  ->  first attempt: ReadTimeout at 30s
                                 retried with a 60s timeout: HTTP 200, {"value":[]}
    api-version=2023-05-01  ->  HTTP 200, {"value":[]}
    api-version=2021-10-01  ->  HTTP 200, {"value":[]}

**No permission/auth error at any point, on any version.** The 2024-08-01
timeout on the first attempt looked like one-off connection/cold-start
latency (first HTTPS handshake to management.azure.com), not a real problem
with that specific API version - confirmed by retrying with a longer timeout
and getting an immediate 200. Not something that needed CLAUDE.md's
"security-relevant change, Edson's call" hard stop - there was no permission
gap to work around, so that branch of the task never applied.

**Why the empty result is very likely genuine, not a bug:** this matches
exactly what Tasks 9-11 already found about this subscription's usage
history. The one real VM (NISE-DEV) was created 2026-06-14 but has real,
substantial cost gaps (Task 8 found only 6 of a 30-day window had actual VM
cost records; Task 11 found only 3 days of CPU history against a 14-day
window) - i.e. it's been powered off for large stretches, not run
continuously long enough to look like "steady-state on-demand usage" to
Azure's own reservation-recommendation engine, which needs a sustained usage
pattern (typically a rolling lookback window of consistent hours) before it
will suggest a commitment. An empty result from an engine designed to avoid
recommending a 1-3 year commitment against spotty, short-lived usage is the
expected behavior here, not a failure - same conclusion this task's own text
predicted ("plausible given this dev subscription's usage patterns").

## Phase 2: Build

### Files changed/added

- `backend/app/services/reserved_instances.py` (new):
  - `fetch_reservation_recommendations(subscription_id)` - the live call,
    using raw REST via `httpx` + `azure-identity`'s `ClientSecretCredential`
    (both already dependencies), not the `azure-mgmt-consumption` SDK - see
    design decision #1 below.
  - `map_recommendation(item)` - normalizes one raw API item into a shape
    roughly consistent with the other recommendation endpoints (resource
    type, scope, an estimated savings figure) without forcing fields Azure's
    response doesn't naturally have into that shape, and preserves the full
    raw item under `raw` on every mapped result - see design decision #2.
  - `build_reservation_recommendations(fetch=fetch_reservation_recommendations)` -
    the same fetch-injection pattern `sync_inventory`/`sync_utilization`/
    `sync_cost` already use, specifically so the automated test suite never
    needs live credentials.
- `backend/app/api/recommendations.py` - added `GET
  /api/v1/recommendations/reserved-instances`. Deliberately has no `db`
  dependency, unlike the other three recommendation routes - there's nothing
  in this app's own database this endpoint reads or writes.
- `backend/tests/test_reserved_instances.py` (new, 6 tests) - field
  extraction from a realistic fixture item, raw-item preservation, a missing-
  properties case that doesn't crash, mapping multiple items, the actual
  real-world empty-result shape treated as a success case (not an error
  path), and confirming the configured subscription ID is what actually gets
  passed to fetch.

### Design decisions (flagged explicitly, not silently assumed)

1. **Raw REST + `httpx`, not the `azure-mgmt-consumption` SDK.** The task
   explicitly allowed either. Phase 1's investigation script already proved
   the raw REST call works end-to-end with the existing credentials, and
   it's a single GET with no request body or complex parameters - adding a
   new SDK dependency (and its own auth/client wiring) for that one call
   wasn't justified when `httpx` and `azure-identity` (for the token) are
   already dependencies used elsewhere in the codebase.

2. **Field names in `map_recommendation()` are NOT verified against real
   populated data, and this is stated plainly in three places: a code
   comment, a module-level `FIELD_MAPPING_NOTE` constant, and the `
   field_mapping_note` key in the actual API response.** This is a real
   departure from Tasks 9/10's practice of checking field names against a
   real synced/returned item before building on them - here that's
   structurally impossible, because Phase 1's live call returned zero items
   to check field names against. The mapping is based on Microsoft's
   documented schema for this API, which could be wrong or could drift. The
   mitigation: every mapped recommendation carries the complete, unmodified
   raw API item under `raw`, so nothing is lost if a mapped field name turns
   out to be wrong once this subscription (or another one) actually produces
   a populated response - the fix at that point would be a mapping
   correction, not a re-fetch.

3. **No `db` dependency on the endpoint, and no persistence.** The task was
   explicit about this ("don't force this into the compute-on-read-from-DB
   pattern") and the underlying reason holds: this app has no local copy of
   whatever internal usage history Azure's recommendation engine actually
   uses, and doesn't need one - recomputing or caching Azure's own analysis
   locally would just be a staleness risk with no benefit over calling
   Azure's engine directly each time.

4. **Request timeout set to 60s, informed directly by what actually
   happened in Phase 1** (a 30s timeout failed once, a 60s timeout succeeded
   immediately on the same call) rather than picking an arbitrary number -
   this is ordinary cold-connection variance to a management API, not
   something to silently retry-loop around or ignore.

5. **No HTTP-level `TestClient` test for this endpoint**, unlike the other
   three recommendation endpoints. Those are DB-only, so a `TestClient` call
   never leaves the test process. This endpoint's default `fetch` parameter
   is a live external call - routing an HTTP-level test through the actual
   FastAPI route would either need live credentials in the test suite
   (violates the "no live credentials needed for pytest" principle the task
   itself invoked) or patching a function reference bound as a default
   argument at import time (fragile, low signal). The route itself is a
   one-line pass-through to `build_reservation_recommendations()`, which is
   thoroughly unit-tested with a mocked `fetch`; the actual live wiring is
   verified by the live check below instead, same as Phase 1's own
   investigation already did.

+    resources, non-peak scheduling), which are compute-on-read against data
