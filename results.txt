# TASK 9 RESULTS - Recommendations: Rightsizing

## Summary

Added `GET /api/v1/recommendations/rightsizing`, compute-on-read against
`utilization_metrics`, `resources`, and `cost_records` already in the DB - no
new external calls, no persistence. For each VM and App Service, it computes
average CPU over the trailing `idle_lookback_days` window (Task 5's setting,
not a new one), flags anything below `idle_cpu_threshold_percent` (also Task
5's), suggests a smaller VM SKU via a core-count-halving heuristic (explicitly
labeled as a naming-pattern guess, not a live Azure availability check), and
estimates monthly savings from `cost_records` (explicitly labeled
approximate). Resources with less utilization history than the lookback
window are excluded outright, not flagged on partial data - same principle as
the forecasting model's "insufficient data" handling from Task 7/8.

All 50 tests pass (20 new). Live check against the real subscription returns
an empty recommendation list, and that's the *correct* answer given the real
data currently in the DB - see "Live check" below for why, which is itself a
demonstration that the insufficient-history exclusion rule is working as
specified rather than a null result I'm asking you to take on faith.

## Design decisions (flagged explicitly, not silently assumed)

1. **App Service tier suggestion: declined entirely, not attempted.** App
   Service Plan tiers ("S1", "P2v3", "B1") encode a pricing/feature tier, not
   a linear compute unit - there's no core-count-style number to halve that
   reliably lands on a valid smaller tier (P2v3 -> "half of 2"? S1 has no
   smaller S-tier; B/S/P families aren't ordered the same way). The task text
   explicitly sanctions this ("it is fine to flag App Services... without a
   specific suggested tier... explain whichever way you go"), so I took that
   path rather than inventing an ordinal "one size down" heuristic that would
   have added complexity and a second, differently-shaped guess to justify.
   App Services are still flagged as candidates when idle - just with
   `suggested_sku: null` and a note explaining why.

2. **Savings estimate reuses `LinearBurnRateModel` rather than reimplementing
   windowing.** The estimate needs "average daily cost over the lookback
   window" for a resource - exactly what Task 8's calendar-day, zero-fill,
   gap-aware windowing already computes for forecasting. Instead of writing a
   second version of that logic, `rightsizing.py` calls
   `LinearBurnRateModel(trailing_window_days=idle_lookback_days).forecast(...)`
   on the resource's own daily costs and takes `daily_rate` as the average.
   This also means a VM with a cost gap (powered off partway through the
   window) gets the same correct zero-filled average here as it would in a
   forecast for that VM - one tested implementation, not two.

3. **Savings math: `avg_daily_cost * cores_reduction_fraction * 30`.** This
   assumes cost scales linearly with core count within the same VM series,
   which is not exactly true (Azure pricing isn't perfectly linear per core
   across a series) but is a defensible v1 approximation - and the response's
   `savings_note` says so explicitly on every recommendation that has a
   number, rather than presenting it as precise. When there's no specific
   suggested SKU (App Service, or a VM SKU the heuristic couldn't parse),
   `estimated_monthly_savings` is `null` with a note explaining there's
   nothing to scale against - I did not fall back to "resource is idle, so
   assume 100% savings" or any other made-up fraction.

4. **"Insufficient history" is judged from the data itself, not wall-clock
   `now()`.** Same reasoning as Task 8's forecasting fix: bases the window on
   the most recent *reading* for that resource+metric, not on
   `datetime.now()`, so a resource whose last sync happened a few hours ago
   isn't penalized by clock skew between sync runs and the request. A
   resource's span (earliest reading's date to most recent reading's date,
   inclusive) must be `>= idle_lookback_days`, or it's excluded outright.

5. **VM SKU regex deliberately fails closed on irregular patterns** (e.g.
   constrained-core SKUs like "Standard_E8-4s_v5", which have a dash embedded
   in the size code). Rather than special-casing that pattern to produce a
   plausible-looking but unverified suggestion, the regex simply doesn't
   match it, and the resource is flagged as a candidate with `suggested_sku:
   null` and a note naming the exact SKU that didn't parse. Same "don't force
   a bad guess" principle the task calls out for App Service tiers, applied
   consistently to the VM side too even though the task only spelled it out
   for App Service.

+import re

+# Matches the size-code segment of an Azure VM SKU (e.g. "D4s" in
+# "Standard_D4s_v3", "B2ms" in "Standard_B2ms"): letters (family), a digit run
+# (core count), then more letters (feature suffix - "s" = premium storage,
+# "ms"/"as" etc). Deliberately does NOT match constrained-core / specialty
+# patterns with an embedded dash (e.g. "E8-4s") - those fail to match and fall
+# through to "no suggestion" rather than being mangled by a naive halving.
+_VM_SIZE_RE = re.compile(r"^(?P<family>[A-Za-z]+)(?P<cores>\d+)(?P<suffix>[A-Za-z]*)$")

+
+@dataclass
+class SkuSuggestion:
+    suggested_sku: str | None
+    note: str
+    cores_reduction_fraction: float | None
+
+
+def suggest_vm_sku(sku: str | None) -> SkuSuggestion:
+    """Suggest a smaller VM SKU by parsing the core-count component and
+    roughly halving it, staying within the same family/suffix/version.
+
+    This is a naming-pattern heuristic only, not a live Azure SKU availability
+    or quota check - see the note on the returned SkuSuggestion, which is
+    always populated (even when no specific SKU is suggested) so the caller
+    never has to guess why.
+    """
+    if not sku:
+        return SkuSuggestion(None, "No SKU recorded for this resource; cannot suggest a smaller size.", None)
+
+    parts = sku.split("_")
+    if len(parts) < 2:
+        return SkuSuggestion(
+            None,
+            f"SKU '{sku}' does not match the expected <Tier>_<Size> naming pattern; cannot parse a core count.",
+            None,
+        )
+
+    size_code = parts[1]
+    match = _VM_SIZE_RE.match(size_code)
+    if not match:
+        return SkuSuggestion(
+            None,
+            f"SKU '{sku}' has a size component ('{size_code}') that doesn't match the simple "
+            "<family><cores><suffix> pattern this heuristic parses (e.g. a constrained-core or "
+            "specialty SKU) - flagging as a rightsizing candidate without a specific suggestion "
+            "rather than force a bad guess.",
+            None,
+        )
+
+    cores = int(match.group("cores"))
+    if cores <= 1:
+        return SkuSuggestion(
+            None, f"SKU '{sku}' is already at the smallest core count this heuristic recognizes.", None
+        )
+
+    suggested_cores = max(1, cores // 2)
+    new_size_code = f"{match.group('family')}{suggested_cores}{match.group('suffix')}"
+    parts[1] = new_size_code
+    suggested_sku = "_".join(parts)
+    note = (
+        f"Heuristic suggestion only: parsed the core-count component of '{sku}' and halved it "
+        f"within the same series/family/version. This is not a live Azure SKU availability or "
+        f"quota check - '{suggested_sku}' may not actually be available in this region. Verify "
+        "before resizing."
+    )
+    return SkuSuggestion(suggested_sku, note, 1 - (suggested_cores / cores))
+
+
+def suggest_app_service_tier(sku: str | None) -> SkuSuggestion:
+    """App Service Plan tier names (e.g. 'S1', 'P2v3', 'B1') encode a
+    pricing/feature tier rather than a linear compute unit the way VM series
+    sizes do, so there's no clean equivalent of "parse the number, halve it"
+    that reliably lands on a valid smaller tier. Per the task's own guidance,
+    flag as a rightsizing candidate without a specific suggested tier rather
+    than force a bad guess.
+    """
+    return SkuSuggestion(
+        None,
+        "App Service tier naming (pricing/feature tier, not a linear compute unit) doesn't map "
+        "cleanly to a 'suggest a smaller one' heuristic the way VM SKUs do - flagged as a "
+        "rightsizing candidate without a specific suggested tier.",
+        None,
+    )

+from dataclasses import dataclass
+from datetime import datetime, timedelta
+
+
+@dataclass
+class CpuUtilizationResult:
+    avg_cpu_percent: float | None
+    insufficient_data: bool
+    is_idle: bool
+
+
+def evaluate_cpu_utilization(
+    readings: list[tuple[datetime, float]],
+    lookback_days: int,
+    idle_threshold_percent: float,
+) -> CpuUtilizationResult:
+    """Average CPU% over the trailing `lookback_days` window ending on the most
+    recent reading, and flag idleness against `idle_threshold_percent`.
+
+    `readings` need not be sorted. A resource whose earliest reading doesn't
+    reach back far enough to cover the full lookback window has
+    insufficient_data=True - it must be excluded from results entirely rather
+    than flagged (or cleared) on a partial average, mirroring the forecasting
+    model's "insufficient data" handling (Task 7/8).
+    """
+    if not readings:
+        return CpuUtilizationResult(avg_cpu_percent=None, insufficient_data=True, is_idle=False)
+
+    timestamps = [ts for ts, _ in readings]
+    most_recent = max(timestamps)
+    earliest = min(timestamps)
+    span_days = (most_recent.date() - earliest.date()).days + 1
+    if span_days < lookback_days:
+        return CpuUtilizationResult(avg_cpu_percent=None, insufficient_data=True, is_idle=False)
+
+    window_start_date = most_recent.date() - timedelta(days=lookback_days - 1)
+    window_values = [value for ts, value in readings if ts.date() >= window_start_date]
+    avg_cpu_percent = sum(window_values) / len(window_values)
+    return CpuUtilizationResult(
+        avg_cpu_percent=avg_cpu_percent,
+        insufficient_data=False,
+        is_idle=avg_cpu_percent < idle_threshold_percent,
+    )
