# TASK 20 RESULTS - AWS Recommendations (mocked AWS API, no live account required)

## Summary

Built all four AWS recommendation categories mirroring Tasks 9/11/12's Azure
implementations, reusing the fully-generic pieces of that code directly (non-prod
heuristics, peak/off-peak usage evaluation, CPU idle evaluation) rather than
reimplementing them, and writing AWS-specific equivalents only where the real
underlying concept genuinely differs (SKU-suggestion heuristic, idle-state
detection). Wired all four into the existing `/api/v1/recommendations/*` endpoints
so Azure's own results are unchanged and AWS's are only appended when configured.
Along the way, built the AWS CloudWatch utilization connector (`aws_utilization.py`)
that wasn't built in Task 19 but that rightsizing/non-peak-scheduling both need, and
extended `aws_inventory.py`'s enrichment to capture the resource-state fields
idle-resource detection needs (none of which existed before this task). Investigated
AWS Compute Optimizer (confirmed not usable in v1, and confirmed moto can't even
simulate it) and both RI/Savings Plan recommendation APIs (confirmed moto can't
simulate either, but the investigation itself caught a real, load-bearing bug in
Task 19's `aws_cost.py` that would have broken cost sync against a real account -
fixed here). 195 backend tests passing (127 pre-existing Azure/shared tests
completely untouched + 68 AWS-specific, 52 new here), 34 frontend tests passing.
Live-verified zero Azure
regression across sync, all four recommendation endpoints, and the dashboard UI.

## Item 1: AWS Compute Optimizer investigation

Real, verified findings (not assumed):
- Compute Optimizer requires an explicit account-level opt-in
  (`UpdateEnrollmentStatus(status='Active')`, checked via `GetEnrollmentStatus`)
  before any of its recommendation APIs (`GetEC2InstanceRecommendations`,
  `GetEBSVolumeRecommendations`, etc.) return anything - not guaranteed on for a
  new/low-usage dev account, same "account-level opt-in, not guaranteed on"
  category of prerequisite Task 19 found for Cost Explorer's "Resource IDs"
  setting.
- **moto does not implement Compute Optimizer at all** - confirmed directly:
  `client.get_enrollment_status()` and `client.get_ec2_instance_recommendations()`
  both return `404 Not yet implemented` against `@mock_aws`. There is no way to
  build or test against Compute Optimizer using this project's mocking strategy
  even if v1 wanted to.
- Per the task's own instruction, v1 does NOT build against Compute Optimizer -
  the CloudWatch-heuristic rightsizing path (`aws_rightsizing.py`) is the actual
  v1 implementation, unconditionally. This section is purely the requested
  investigation note for a possible future task once a real account with
  Compute Optimizer opted in exists.

## Item 4: RI/Savings Plan recommendation API findings

Real, verified findings from actually calling these operations against `@mock_aws`,
not assumed from documentation alone:

- **`get_reservation_purchase_recommendation`**: `NotImplementedError` - moto does
  not implement this operation at all.
- **`get_savings_plans_purchase_recommendation`**: same - `NotImplementedError`,
  not implemented in moto.
- **Real prerequisite** (from AWS's own documented behavior, since moto can't be
  used to verify this empirically): both APIs need a meaningful, consistent amount
  of On-Demand usage history before producing anything - informally "several
  weeks" per AWS's docs. This is the same category of "empty result on low usage
  history, not a bug" finding Task 12 made for Azure's reservationRecommendations
  API, and Task 19 made for AWS's own resource-level Cost Explorer data.
- **What's genuinely unverifiable until Task 21**: whether these two calls
  actually succeed and return a well-formed response against the real account at
  all (field names, nesting, whether an empty result really means "not enough
  history" vs. some other real error) - none of that can be confirmed without a
  live account with real usage history, exactly as the task anticipated. Built
  `aws_reserved_instances.py`'s `fetch_reservation_recommendations`/
  `fetch_savings_plans_recommendations` against AWS's documented request/response
  shapes, and tested the surrounding logic (`map_reservation_recommendation`/
  `map_savings_plan_recommendation`/`build_aws_reservation_recommendations`)
  against hand-built fixtures matching those documented shapes (mirroring
  `reserved_instances.py`'s own test convention, which never called the real
  Azure SDK either) - did not force a fake "it works end-to-end" result, per the
  task's explicit instruction not to.
- **A real bug the RI/Savings-Plan investigation indirectly caught in Task 19's
  code**: while confirming what moto could and couldn't simulate for Cost
  Explorer generally, also tried the previously-untested real
  `get_cost_and_usage_with_resources` call (Task 19's own resource-level cost
  API) against `@mock_aws` for the first time - it failed with
  `botocore.exceptions.ParamValidationError: Missing required parameter in
  input: "Filter"`. This is a **real, load-bearing bug**: `GetCostAndUsageWithResources`
  has a required `Filter` parameter that plain `GetCostAndUsage` doesn't, and
  Task 19's original call never passed one - all of Task 19's own tests used
  injected fake fetch functions, so this was never actually exercised against
  real boto3/botocore parameter validation before now. Would have failed the
  very first time Task 21 tried to sync AWS cost data against a real account,
  not just against moto. **Fixed here**: added `Filter={"Dimensions": {"Key":
  "LINKED_ACCOUNT", "Values": [account_id]}}` - broad/non-restrictive for the
  standalone (non-Organizations) account GOV-002 2.1 describes, satisfying the
  requirement without meaningfully narrowing scope. Flagged for Task 21 to
  re-verify if the real account turns out to be an AWS Organizations member
  account (a related edge case GOV-002 2.1 itself already flagged for Cost
  Explorer generally). Added a regression test
  (`test_fetch_cost_rows_call_is_well_formed`) confirming the call passes
  botocore's parameter validation (the only thing verifiable pre-moto-support -
  moto raises `NotImplementedError` for this operation at the server level
  regardless of whether parameters are valid, confirmed directly).

This fix is flagged prominently as a genuine correction to already-shipped Task
19 code, found only because Task 20's own investigation happened to exercise a
code path Task 19's tests never did - not something silently bundled in.

## Other real AWS API findings from writing the moto mocks

- **moto's Tagging API does not discover Elastic IPs at all**, even tagged ones -
  confirmed directly: `get_resources()` returns an empty list for an allocated
  and tagged Elastic IP, while `describe_addresses()` on the same resource
  correctly shows the tag. This is a moto-specific gap, not real AWS behavior
  (AWS's real Tagging API does return Elastic IPs) - real EIP discovery via the
  Tagging API is untestable end-to-end against moto for exactly this reason.
  `aws_inventory._enrich_elastic_ips` (which calls `describe_addresses`
  directly, given a list of allocation IDs) is still testable and tested against
  real moto EC2 calls - only the "discover an EIP via tagging in the first
  place" half of the pipeline can't be verified pre-Task-21. Flagged explicitly
  for Task 21 to specifically check EIP discovery against the real account.
- CloudWatch's real "no data" behavior differs from Azure Monitor's: a metric
  with nothing to report returns a normal 200 response with an empty
  `Datapoints` list, not an error - unlike Azure Monitor's `HttpResponseError`
  for a metric that isn't valid for a given resource (which
  `azure_utilization.py` has to catch and treat as "no data"). Nothing
  equivalent to catch in `aws_utilization.fetch_metrics` - confirmed this isn't
  an oversight, it's a genuine API-behavior difference.
- `get_metric_statistics` (CloudWatch) and `describe_instances`/`describe_volumes`/
  `describe_addresses`/`put_metric_data` (EC2) are all well-supported by moto -
  confirmed via real end-to-end moto tests (`test_fetch_metrics_moto_real_cloudwatch_call`,
  the EC2 instance/volume enrichment tests, the Elastic IP enrichment test) that
  actually call these operations, not just injected fixtures.

## What was built

**`aws_cpu_metrics.py`**: `AWS_CPU_METRIC_BY_RESOURCE_TYPE` mapping, mirrors
`cpu_metrics.py`. EC2 only for v1 (GOV-002 2.3's own scoping).

**`aws_utilization.py`**: CloudWatch `GetMetricStatistics` sync, mirrors
`azure_utilization.py`. Namespace/dimension-name lookup per resource type
(`AWS/EC2`/`InstanceId` for EC2) since CloudWatch, unlike Azure Monitor's
`query_resource`, needs these supplied explicitly rather than resolving them
from a single resource URI. Reads the real AWS resource ID from
`raw_metadata["resource_id"]` (populated by `aws_inventory.parse_arn` during
inventory sync), not the ARN.

**`aws_inventory.py` extended** (not new, Task 19's file): `_enrich_ec2_instances`
and `_enrich_ebs_volumes` now also capture `state` (`running`/`stopped` for
instances, `available`/`in-use` for volumes); new `_enrich_elastic_ips` (calls
`describe_addresses`, wasn't in Task 19's two-type enrichment scope at all) captures
`associated`. All three feed idle-resource detection, none of which existed before
this task needed them.

**`aws_idle_resource_detection.py`** (mirrors `idle_resource_detection.py`): three
pure detection functions reading already-synced `raw_metadata` - unattached EBS
volume (`state == "available"`), unassociated Elastic IP (`associated == False`),
stopped EC2 instance (`state == "stopped"`). The stopped-instance detail text is
deliberately accurate about AWS's real billing behavior (a stopped EC2 instance
does NOT bill for compute, unlike Azure's "stopped but not deallocated" which
does) rather than copying Azure's framing verbatim - the real waste is whatever's
still attached (EBS, an EIP that loses its running-instance exemption).

**`aws_idle_resources.py`** (mirrors `idle_resources.py`): orchestration, same
shape, `estimate_monthly_waste` re-worded for AWS's own remediation steps
(volume/EIP/instance, not disk/IP/VM).

**`aws_sku_heuristics.py`**: `suggest_ec2_instance_type` - AWS's size-name
convention (`t3.micro`, `m5.xlarge`) has no parseable core-count the way Azure's
`Standard_D4s_v3` does, so this steps down one size on AWS's standard
nano→48xlarge ladder within the same family, instead of parsing-and-halving a
number. A ladder step is AWS's own "roughly double resources per step"
convention, so `cores_reduction_fraction` is approximated at a flat 0.5 - not a
guess, an explicit reading of how AWS's own naming convention is designed.

**`aws_rightsizing.py`** (mirrors `rightsizing.py`): reuses
`utilization_evaluation.evaluate_cpu_utilization` directly (confirmed
Azure-agnostic before reusing), EC2-only for v1.

**`aws_non_peak_scheduling.py`** (mirrors `non_peak_scheduling.py`): reuses
`non_prod_heuristics.detect_non_prod_by_tag`/`detect_non_prod_by_name` and
`peak_usage_evaluation.evaluate_peak_off_peak_usage` directly (both confirmed
Azure-agnostic before reusing - neither module has an Azure-specific assumption
anywhere). One small, deliberate improvement over Azure's own file: reads
`resource.name` (the real column, Task 16) directly rather than Azure's
`non_peak_scheduling.py`'s still-stale `raw_metadata.get("name")` pattern (a
pre-existing Task-16-era staleness in Azure's own code, not touched here per
"don't change Azure's existing behavior," but not copied into new AWS code either).

**`aws_reserved_instances.py`**: both `GetReservationPurchaseRecommendation` and
`GetSavingsPlansPurchaseRecommendation`, merged into one response
(`recommendation_type: "reserved_instance" | "savings_plan"` distinguishes them) -
GOV-002 2.5 treats both as "the 4th category," and this task's item 5 wants AWS
merged into the single existing `/reserved-instances` endpoint, so both AWS APIs
merge into one list the same way. See the dedicated investigation section above.

**API wiring**: `POST /api/v1/utilization/sync` and all four
`GET /api/v1/recommendations/*` endpoints now conditionally call the AWS
equivalent and merge/sum results, only when `settings.aws_configured` - exact
same pattern Task 19 established for inventory/cost sync, confirmed live to leave
Azure's own responses byte-identical when AWS is unconfigured.

**`provider` field added to every recommendation item** (Azure's existing
builders too - rightsizing, idle-resources, non-peak-scheduling, reserved-
instances - plus their AWS equivalents): additive field, needed once both
providers' items land in the same merged list so the frontend (and anyone
reading the API directly) can tell them apart without inferring it from
`resource_type`'s string prefix.

**Frontend** (`types.ts`, `normalizeRecommendations.ts`): added `provider` to the
three shared-shape recommendation types (Rightsizing/IdleResource/
NonPeakScheduling - no logic changes needed there, the field sets are identical
between providers, only values differ). `ReservedInstanceRecommendation` genuinely
needed reshaping: AWS's two recommendation kinds use entirely different field
names than Azure's single API (`instance_type`/`hourly_commitment` vs.
`sku`/`scope`), not just different values - every field is now optional, and
`normalizeReservedInstances` branches on `provider`/`recommendation_type` to
build the right title/reason per shape rather than assuming Azure's shape fits
AWS's data (which would have silently produced blank/garbage cards for every AWS
reservation recommendation once merged in, since none of Azure's field names
exist on an AWS item). No other hardcoded Azure-specific copy found needing a
fix - `normalizeRightsizing`'s "SKU" terminology is a UI label describing a
Azure/AWS-agnostic response field (`current_sku`/`suggested_sku`, used by both
providers with their own native values, e.g. `t3.micro` reads fine there without
being technically called a "SKU" by AWS) rather than something blocking AWS data.

**Minor known limitation, not fixed**: the merged reserved-instances response's
top-level `field_mapping_note` reflects only Azure's own note text when both
providers have items (the AWS branch's own note gets appended as recommendation
items, not merged at the top level) - both notes carry the same substantive "not
verified against real populated data" caveat, just worded slightly differently
per provider, so this is a wording-completeness gap, not a functional/misleading
one. Flagged rather than silently accepted; not fixed given the disproportionate
complexity of threading a second top-level note through a response that's
otherwise a flat list, for what's already the same caveat conceptually.

from dataclasses import dataclass

# EBS's own explicit attachment-state field - direct analogue of Azure's
# diskState check. "in-use" is the attached state; "available"/"creating"/
# "deleting"/"error" are the others, but only "available" means unattached.
UNATTACHED_VOLUME_STATE = "available"

# EC2's own explicit instance lifecycle state. Unlike Azure's "stopped but not
# deallocated" (which keeps billing compute), a stopped EC2 instance does NOT
# bill for compute - only for anything still attached (EBS volumes, an
# Elastic IP no longer covered by a running-instance exemption). Flagged as
# a real analogue of Task 9's check per the task's own instruction, but the
# detail text below is accurate about what's actually still billing, not a
# copy-paste of Azure's compute-waste framing.
STOPPED_INSTANCE_STATE = "stopped"


@dataclass
class IdleCheckResult:
    is_flagged: bool
    detail: str


def detect_unattached_ebs_volume(raw_metadata: dict) -> IdleCheckResult:
    """Flag an EBS volume with state == "available" (unattached).

    Mirrors azure_idle_resource_detection.detect_unattached_disk - reads the
    `state` field aws_inventory._enrich_ebs_volumes already stores in
    raw_metadata during sync, not a live call at recommendation time.
    """
    state = raw_metadata.get("state")
    if state is None:
        return IdleCheckResult(
            False, "state is not present in the synced metadata; attachment state can't be determined."
        )
    if state == UNATTACHED_VOLUME_STATE:
        return IdleCheckResult(True, f"state is '{state}' (unattached).")
    return IdleCheckResult(False, f"state is '{state}', not '{UNATTACHED_VOLUME_STATE}'.")


def detect_unassociated_elastic_ip(raw_metadata: dict) -> IdleCheckResult:
    """Flag an Elastic IP with no InstanceId/NetworkInterfaceId association.

    Mirrors azure_idle_resource_detection.detect_unused_public_ip. Reads the
    `associated` boolean aws_inventory._enrich_elastic_ips stores.
    """
    associated = raw_metadata.get("associated")
    if associated is None:
        return IdleCheckResult(
            False, "associated is not present in the synced metadata; association state can't be determined."
        )
    if associated:
        return IdleCheckResult(False, "associated with an instance or network interface.")
    return IdleCheckResult(True, "not associated with any instance or network interface - still billed hourly while unattached.")


def detect_stopped_ec2_instance(raw_metadata: dict) -> IdleCheckResult:
    """Flag an EC2 instance whose state is 'stopped'.

    Real difference from Azure's equivalent check, stated plainly rather than
    glossed over: a stopped EC2 instance does NOT bill for compute (unlike
    Azure's "stopped but not deallocated", which does) - the waste here is
    whatever's still attached and billing (EBS volumes, an Elastic IP that
    loses its running-instance fee exemption once stopped), not idle compute
    itself. Still a real, worth-flagging state - a stopped instance is easy to
    forget about - just not the same kind of waste as Azure's check.
    """
    state = raw_metadata.get("state")
    if state is None:
        return IdleCheckResult(False, "state is not present in the synced metadata; instance state can't be determined.")
    if state == STOPPED_INSTANCE_STATE:
        return IdleCheckResult(
            True,
            f"state is '{state}' - not billing compute, but any attached EBS volumes or an Elastic IP "
            "(which loses its running-instance fee exemption once stopped) still are.",
        )
    return IdleCheckResult(False, f"state is '{state}', not '{STOPPED_INSTANCE_STATE}'.")

    "small",
    "medium",
    "large",
    "xlarge",

# Each ladder step is AWS's own "roughly double resources" convention, so a
# one-step-down suggestion is approximately a 50% reduction - used the same
# way sku_heuristics' parsed core-halving informs its own savings-scale
# fraction, just via AWS's naming convention instead of a parsed number.
_STEP_DOWN_REDUCTION_FRACTION = 0.5


def suggest_ec2_instance_type(instance_type: str | None) -> SkuSuggestion:
    """Suggest a smaller EC2 instance type by stepping down one size on AWS's
    standard size ladder, staying within the same family/generation.

    A naming-pattern heuristic only, not a live AWS instance-type availability
    or quota check - mirrors sku_heuristics.suggest_vm_sku's own disclaimer,
    adapted to AWS's discrete-size-name convention instead of Azure's
    parseable core-count.
    """
    if not instance_type:
        return SkuSuggestion(None, "No instance type recorded for this resource; cannot suggest a smaller size.", None)

    if "." not in instance_type:
        return SkuSuggestion(
            None,
            f"Instance type '{instance_type}' does not match the expected <family>.<size> naming pattern; "
            "cannot parse a size.",
            None,
        )

    family, size = instance_type.split(".", 1)
    if size not in _SIZE_LADDER:
        return SkuSuggestion(
            None,
            f"Instance type '{instance_type}' has a size ('{size}') outside the standard "
            "nano..48xlarge steps this heuristic recognizes (e.g. a specialty/metal size) - flagging as a "
            "rightsizing candidate without a specific suggestion rather than force a bad guess.",
            None,
        )

    index = _SIZE_LADDER.index(size)
    if index == 0:
        return SkuSuggestion(
            None, f"Instance type '{instance_type}' is already at the smallest size this heuristic recognizes.", None
        )

    suggested_type = f"{family}.{_SIZE_LADDER[index - 1]}"
    note = (
        f"Heuristic suggestion only: stepped '{instance_type}' down one size on AWS's standard size ladder, "
        f"within the same instance family. This is not a live AWS instance-type availability or quota check - "
        f"'{suggested_type}' may not actually be available in this region/AZ. Verify before resizing."
    )
    return SkuSuggestion(suggested_type, note, _STEP_DOWN_REDUCTION_FRACTION)

import uuid

import boto3

from app.core.config import settings

# Not explicitly listed as its own scope item in Task 20's text, but inferred
# as a necessary prerequisite: rightsizing and non-peak-scheduling both read
# CPU utilization from the already-synced UtilizationMetric table (same
# sync-then-read architecture as Azure, not a live call at recommendation
# time), and nothing built that sync path for AWS before this task - Task 19
# only covered inventory and cost. Mirrors azure_utilization.py's shape.

GRANULARITY_SECONDS = 3600  # 1 hour, matching azure_utilization.GRANULARITY

# Namespace + dimension name CloudWatch needs to identify a resource's metrics
# - unlike Azure Monitor's query_resource (which takes the full ARM resource
# URI and resolves this itself), CloudWatch needs these supplied explicitly
# per service. Only EC2 for v1 (see aws_cpu_metrics.py).
_NAMESPACE_AND_DIMENSION_BY_RESOURCE_TYPE: dict[str, tuple[str, str]] = {
    "aws::ec2::instance": ("AWS/EC2", "InstanceId"),
}


@dataclass
class AwsUtilizationSyncSummary:
    resources_processed: int
    metrics_found: int
    created: int
    updated: int


def map_metric_response(response: Any, metric_name: str) -> list[dict[str, Any]]:
    """Flatten one CloudWatch GetMetricStatistics response into normalized rows.

    A datapoint with no Average is skipped - mirrors azure_utilization's own
    "gap in the series" handling, though real API-shape difference worth
    noting: CloudWatch's documented behavior is to simply omit a period with no
    data from Datapoints entirely, never return a point with a null Average -
    this check is defensive, not something observed happening.
    """
    rows: list[dict[str, Any]] = []
    for point in response.get("Datapoints", []):
        if point.get("Average") is None:
            continue
        rows.append(
            {
                "metric_name": metric_name,
                "unit": point.get("Unit", "Percent"),
                "timestamp": point["Timestamp"],
                "value": point["Average"],
            }
        )
    return rows


def _query_metric(
    client: Any, namespace: str, dimension_name: str, resource_id: str, metric_name: str, lookback_days: int
) -> Any:
    end = datetime.now(timezone.utc)
    start = end - timedelta(days=lookback_days)
    return client.get_metric_statistics(
        Namespace=namespace,
        MetricName=metric_name,
        Dimensions=[{"Name": dimension_name, "Value": resource_id}],
        StartTime=start,
        EndTime=end,
        Period=GRANULARITY_SECONDS,
        Statistics=["Average"],
    )


def fetch_metrics(
    resource_type: str,
    resource_id: str,
    metric_names: list[str],
    lookback_days: int,
    query_metric: Callable[[str, str, str, str, int], Any] | None = None,
) -> list[dict[str, Any]]:
    """Query CloudWatch for each named metric on a single resource.

    Real API-shape difference from Azure Monitor, found writing this: a metric
    CloudWatch has no data for returns a normal response with an empty
    Datapoints list, not an error - unlike Azure Monitor's HttpResponseError
    for a metric that isn't valid for a given resource (which azure_utilization
    catches and treats as "no data for this metric"). Nothing to catch here;
    map_metric_response naturally produces zero rows for an empty response.
    """
    namespace, dimension_name = _NAMESPACE_AND_DIMENSION_BY_RESOURCE_TYPE[resource_type]
    if query_metric is None:
        session = boto3.Session(
            aws_access_key_id=settings.aws_access_key_id,
            aws_secret_access_key=settings.aws_secret_access_key,
            region_name=settings.aws_region,
        )
        client = session.client("cloudwatch")
        query_metric = lambda ns, dim, rid, name, days: _query_metric(client, ns, dim, rid, name, days)  # noqa: E731

    rows: list[dict[str, Any]] = []
    for metric_name in metric_names:
        response = query_metric(namespace, dimension_name, resource_id, metric_name, lookback_days)
        rows.extend(map_metric_response(response, metric_name))
    return rows


def upsert_metrics(db: Session, resource_id: uuid.UUID, rows: list[dict[str, Any]]) -> tuple[int, int]:
    created = 0
    updated = 0
    for row in rows:
        existing = (
            db.query(UtilizationMetric)
            .filter_by(resource_id=resource_id, metric_name=row["metric_name"], timestamp=row["timestamp"])
            .one_or_none()
        )
        if existing is None:
            db.add(
                UtilizationMetric(
                    resource_id=resource_id,
                    metric_name=row["metric_name"],
                    timestamp=row["timestamp"],
                    value=row["value"],
                    unit=row["unit"],
                )
            )
            created += 1
        else:
            existing.value = row["value"]
            existing.unit = row["unit"]
            updated += 1
    db.commit()
    return created, updated


def sync_aws_utilization(
    db: Session,
    fetch: Callable[[str, str, list[str], int], list[dict[str, Any]]] = fetch_metrics,
) -> AwsUtilizationSyncSummary:
    resources = db.query(Resource).filter(Resource.resource_type.in_(AWS_CPU_METRIC_BY_RESOURCE_TYPE.keys())).all()

    metrics_found = 0
    created = 0
    updated = 0

    for resource in resources:
        metric_names = [AWS_CPU_METRIC_BY_RESOURCE_TYPE[resource.resource_type]]
        # The instance ID CloudWatch's dimension needs, not the ARN - stored in
        # raw_metadata by aws_inventory.parse_arn during inventory sync.
        raw_resource_id = (resource.raw_metadata or {}).get("resource_id")
        if not raw_resource_id:
            continue
        rows = fetch(resource.resource_type, raw_resource_id, metric_names, settings.idle_lookback_days)
        metrics_found += len(rows)
        c, u = upsert_metrics(db, resource.id, rows)
        created += c
        updated += u

    return AwsUtilizationSyncSummary(
        resources_processed=len(resources),
        metrics_found=metrics_found,
        created=created,
        updated=updated,
    )
