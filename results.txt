# TASK 17 RESULTS - Full Phase 1 (Azure) Regression Pass

## Headline finding

This audit found a critical, live, actively-reproducing bug: **Azure Resource
Graph is now returning a different casing for the VM's ARM resource ID than it did
when Task 2 first synced it**, and the inventory sync's upsert key
(`external_resource_id`, matched case-sensitively) treats the new casing as a brand
new resource instead of the same VM. Doing exactly what this task's own scope item 1
asked ("trigger a fresh sync") created a duplicate resource row in the live dev
database, and that duplicate then **completely breaks cost sync** (500 error, full
traceback below) and **duplicates a recommendation** on the live Recommendations
page. This is not a scenario I constructed to test with - it's what actually happened
when I followed this task's own first instruction. Full detail in item 1 and the
prioritized follow-up list below. Per this task's explicit scope, I have not fixed
it, cleaned it up, or modified any code - only verified, reproduced, and documented
it. **The live dev database currently contains this duplicate row as a direct,
unavoidable result of following this task's instructions**, and cost sync is
currently non-functional until a follow-up task addresses it.

No code was changed this task (`git status` clean except `next_task.txt`, which I
didn't touch) - this is a pure verification/audit task, per its own scope.

## 1. Inventory

**What I did:** Snapshotted the `resources` table before syncing (9 rows). Triggered
`POST /api/v1/inventory/sync` (the task's own instruction). Independently queried
Azure Resource Graph directly via a standalone script (same SDK, bypassing the app's
own `azure_inventory.py` code entirely) to get Azure's actual current state, not
just re-trusting the app's own sync logic. Compared all three: pre-sync DB, post-sync
DB, and the independent live query.

**Result: FAIL (data-integrity bug), with count reconciling correctly otherwise.**

- Independent live Resource Graph query confirms Azure's subscription genuinely has
  **9 resources** right now - matches the pre-sync DB count exactly. Full resource
  list (name, type, resource group) from the independent query matches the DB's
  pre-sync contents 1:1. This part is correct.
- But: `POST /api/v1/inventory/sync` returned `{"found": 9, "created": 1, "updated":
  8}` - it found 9 resources from Azure (correct), but created a **10th row** instead
  of updating the existing VM row, because Azure Resource Graph now returns the VM's
  `id` as
  `/subscriptions/.../resourceGroups/nise-rg/providers/Microsoft.Compute/virtualMachines/nise-dev`
  (all lowercase), while the original Task 2 sync stored it as
  `/subscriptions/.../resourceGroups/NISE-RG/providers/Microsoft.Compute/virtualMachines/NISE-DEV`
  (mixed case) - confirmed by re-running the independent Resource Graph query, which
  right now returns the *disk*'s `id` still in the original uppercase
  (`.../NISE-RG/.../disks/...`) while the *VM*'s `id` has changed to lowercase. Same
  resource group, same sync, two different casings for two different resource types
  - this is Azure's own indexing being inconsistent over time, not a one-off fluke.
- `backend/app/services/azure_inventory.py`'s `upsert_resources` matches existing
  rows via `.filter_by(external_resource_id=mapped["external_resource_id"])` - an
  exact, case-sensitive string match. When Azure returns different casing than last
  time, this doesn't match the existing row, so a new one gets created instead of
  updated.
- Notably, `backend/app/services/azure_cost.py`'s `_resolve_resource_id` *already*
  has a code comment acknowledging this exact problem ("Azure resource IDs are
  canonically case-insensitive, and Cost Management's ResourceId dimension doesn't
  always match Resource Graph's casing... for the same resource") and does a
  case-insensitive `func.lower(...)` comparison - but `upsert_resources`'s own
  upsert key was never given the same treatment, so the exact case-sensitive gap that
  cost-sync's own code was written to defend against is precisely what caused this.
- Confirmed the two VM rows are the same physical Azure VM, not actually two VMs:
  identical `created_at` (both `2026-06-14 20:38:10.731+00`, sourced from Azure's own
  `timeCreated` property), identical `name` ("nise-dev"), identical `resource_group`
  ("nise-rg" - only the `external_resource_id`/`id` field's casing differs).
- `GET /api/v1/inventory` (Task 15's endpoint) correctly reflects the DB's actual
  (now-duplicated) state - confirmed the endpoint layer itself is not the bug, it's
  faithfully serving what's in the table. Also confirmed `resources.name` (Task 16's
  migration) is populated correctly for the new row too (map_resource sets it
  directly now, not just via backfill).

## 2. Utilization

**What I did:** Triggered `POST /api/v1/utilization/sync`. Independently queried
Azure Monitor directly (same SDK, bypassing `azure_utilization.py`) for the VM's
"Percentage CPU" metric over the same 7-day window, and compared averages.

**Result: PASS on data correctness, with a compounding side-effect of the inventory bug.**

- Independent Azure Monitor query: 49 data points over 7 days, average 3.18% CPU.
- App's stored data for the real VM resource (`784c331d...`) after the same sync: 64
  data points, average 3.50% CPU. Same order of magnitude, consistent with real VM
  behavior sampled at slightly different windows (my independent query ran a few
  minutes after the app's sync) - not garbage or obviously wrong numbers. **The
  Azure Monitor connector is pulling genuinely correct data.**
- Side effect of the inventory bug: `sync_utilization` queries *every* resource
  matching `RESOURCE_TYPE_METRICS.keys()` with no dedup by physical resource, so it
  queried Azure Monitor for **both** VM rows. Because Azure Monitor also resolves
  resource URIs case-insensitively, **both rows got real utilization data** for what
  is actually one physical VM (64 CPU readings on the original row, 48 on the
  duplicate, averages 3.50% vs 2.88% - close but not identical, again consistent with
  slightly different query timing between the two sequential per-resource calls, not
  two different VMs). This means the duplicate doesn't stay obviously "empty" for
  long - once utilization re-syncs, it looks like a second real resource with its own
  real metrics, which would make it *harder*, not easier, for someone to notice the
  duplicate later.

**Cost sync is broken:** `POST /api/v1/cost/sync` now returns a 500. Full traceback
(from `docker compose logs backend`):

    File "/app/app/services/azure_cost.py", line 120, in upsert_cost_records
        resource_id = _resolve_resource_id(db, row["external_resource_id"])
    File "/app/app/services/azure_cost.py", line 111, in _resolve_resource_id
        .one_or_none()
    sqlalchemy.exc.MultipleResultsFound: Multiple rows were found when one or none was required

`_resolve_resource_id`'s case-insensitive lookup (`func.lower(Resource.external_resource_id) == external_resource_id.lower()`)
now matches *both* VM rows, and `.one_or_none()` requires 0 or 1. This is the
inventory bug's most severe consequence: **the entire cost-sync endpoint is down
for the whole subscription**, not just for the one affected VM, since the exception
is unhandled and propagates out of the whole sync loop before any `db.commit()`.
Confirmed no partial/corrupt writes resulted - `cost_records` count and latest date
are unchanged from before the failed attempt (`get_db`'s session teardown has no
explicit rollback, but `db.close()` with an uncommitted transaction and
`autocommit=False` discards pending changes, which the unchanged row count confirms
empirically). The practical effect is that cost data is now stuck at 2026-09-17 and
cannot be refreshed until this is fixed - not a data-corruption risk, but a
functionality outage.

## 6. Revisiting the `sumTrailingActual` quirk (Task 16's finding)

**What I did:** Checked whether the "last 30 series entries, not last 30 calendar
days" quirk is visible anywhere beyond the single VM-scoped case Task 16 found, by
checking date-gap coverage at every level/resource type currently in the system.

**Result: confirmed narrowly scoped - not urgent, but real and worth a follow-up.**

| Scope | Entries | Calendar days spanned | Gap-free? |
|---|---|---|---|
| Subscription (unfiltered) | 91 | 91 | Yes |
| `nise-rg` (resource-group level) | 91 | 91 | Yes |
| Disk resource (steady daily storage cost) | 91 | 91 | Yes |
| **VM resource (intermittent compute cost)** | **55** | **83** | **No - 28 gap days** |

The quirk is invisible at the subscription level, invisible at the resource-group
level (because `nise-rg`'s disk carries cost on every single day, filling the
group's series completely even on days the VM itself wasn't billed), and invisible
for the disk resource specifically. It is **only** visible when drilling into a
compute resource whose billing history has real gaps (VM stopped/deallocated some
days) - i.e., exactly the one case Task 16 already found, and no broader than that
in this subscription's current data. It would become visible for any other VM/App
Service resource with a similarly gappy history, which is a realistic case for
FinOps users generally (that's the whole point of tracking idle/stopped resources),
so it's a real bug, not a curiosity.

**My priority recommendation: low-to-medium priority, well-defined quick fix, not
urgent.** Reasoning: it produces a misleading number, not a crash or blocked
workflow (unlike the inventory-duplicate bug above); it only affects the one
resource-level trailing-spend figure, not the chart itself (the chart plots real
dated points either way, so a careful user could infer the gaps from the x-axis);
and the fix is small and well-understood (filter `history.series` by
`date >= mostRecentDate - 30d` instead of `slice(-30)` in
`frontend/src/components/SpendPanel.tsx`'s `sumTrailingActual`). I'd bundle it with
whatever follow-up task next touches `SpendPanel`, rather than a dedicated task on
its own.

## Prioritized follow-up list

1. **[CRITICAL - fix immediately] Case-insensitive resource upsert key.**
   `backend/app/services/azure_inventory.py`'s `upsert_resources` must match
   existing rows case-insensitively (mirror the `func.lower(...)` pattern
   `azure_cost.py`'s `_resolve_resource_id` already uses), not via exact
   `external_resource_id` string equality. Without this, **cost sync stays broken**
   for this subscription indefinitely (every future cost sync attempt will hit the
   same `MultipleResultsFound` crash as long as both VM rows exist), and any other
   resource whose ARM ID casing drifts in Azure's own indexing over time (this is
   apparently an Azure Resource Graph behavior, not specific to this one VM) will
   silently create more duplicates. **Must also include, as part of the same fix, a
   one-time cleanup of the existing duplicate VM row in the live dev database** -
   merging or removing the newer, cost-data-less row (`fa1f955c-5def-499b-b9a2-
   b76766df5100`) - since the bug is now live, not hypothetical, and cost sync can't
   function again until it's resolved. Consider whether `external_resource_id`
   should be stored/compared in a normalized (lowercased) form generally, to close
   this class of bug rather than just this one instance.
2. **[HIGH] Utilization sync should dedupe by physical resource, not resource row.**
   Even after (1) is fixed, `sync_utilization`'s per-`Resource`-row loop with no
   awareness of "these two rows are the same physical resource" is a symptom of the
   same underlying assumption (that DB rows and physical resources are 1:1) - worth
   revisiting alongside (1) so a future case-insensitivity edge case (or any other
   future duplicate-producing bug) doesn't silently double-count API calls and data
   again.
3. **[MEDIUM] `SpendPanel.sumTrailingActual` calendar-day quirk** (Task 16's
   finding, re-confirmed and scoped precisely in item 6 above) - real, but narrow
   impact and simple fix. Bundle with the next task touching `SpendPanel`.
4. **[LOW] Recommendations page has no defense against the same physical resource
   appearing twice** (as seen in item 4) - arguably not worth a dedicated fix once
   (1) is resolved and duplicates can't occur, but if (1)'s fix is delayed, a
   short-term mitigation (e.g., dedupe recommendations by `external_resource_id`
   case-insensitively) could reduce visible confusion in the meantime. I'd defer
   this entirely to (1) being fixed rather than treating it as its own task.
