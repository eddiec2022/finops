# TASK 11 RESULTS - Recommendations: Non-Peak Scheduling

## Summary

Added `GET /api/v1/recommendations/non-peak-scheduling`, compute-on-read,
same philosophy as the other recommendation endpoints. Flags VMs and App
Services as "likely non-production" candidates for a start/stop schedule
using three independent signals per GOV-001 - a tag heuristic, a naming
heuristic, and a peak-vs-off-peak CPU usage pattern - any one is sufficient,
none are required to agree. Recommends a standard weeknight/weekend power-off
template (not a per-resource-optimized schedule) and estimates monthly
savings from the fraction of the week that template would have the resource
off, using the same average-daily-cost-from-cost_records approach as Tasks 9
and 10.

All 104 tests pass (29 new). Live check against the real subscription
returns one recommendation - the real VM, flagged by the naming heuristic
(its name contains "dev") since the real environment has no tags at all on
any resource (checked first, per the task's explicit instruction to verify
before hardcoding). The usage-pattern signal correctly excluded itself
(insufficient history - only 3 days of CPU data against the 14-day window,
consistent with what Tasks 9 and 10 already found about this VM). The
estimated savings figure was hand-verified against the real cost_records
rows and matches exactly - see "Live check" below.

## Design decisions (flagged explicitly, not silently assumed)

1. **Real synced resources have no tags at all - checked first, not assumed.**
   Queried every resource's `tags` column in the real dev DB before writing
   the tag heuristic; all nine rows are `{}`. This doesn't change what the
   tag check does (it's still built exactly as specified, and will work the
   moment any resource actually gets an `environment`/`env` tag), but it does
   mean the live check's positive result comes entirely from the naming
   heuristic today, not the tag one - worth knowing rather than assuming both
   heuristics are equally exercised by the current environment.

2. **`evaluate_peak_off_peak_usage()` is a new function, not a variant of
   Task 9's `evaluate_cpu_utilization()`.** The task explicitly asked for
   this ("don't try to force-fit the existing one") and the real reason
   holds up: `evaluate_cpu_utilization` computes one flat average over a
   trailing window; this needs two averages split by a per-timestamp
   day-of-week/hour-of-day predicate first. Trying to parameterize the
   existing function to do both would have made it harder to read for either
   use, not simpler.

3. **Peak avg of ~0% is not flagged via the usage-pattern signal, even
   though the ratio would trivially be low/undefined.** A resource that's
   idle around the clock has nothing to compute a meaningful peak/off-peak
   *ratio* from - that's rightsizing's job (Task 9), not this check's. Rather
   than dividing by a near-zero number or defining an arbitrary "peak is 0 so
   treat ratio as flagged" rule, this case explicitly returns
   `is_flagged: False` with a note saying why. Covered by
   `test_evaluate_peak_off_peak_usage_zero_peak_is_not_flagged`.

4. **A window missing readings in either bucket entirely is
   `insufficient_data`, not a one-sided comparison.** If every reading in the
   trailing window happens to fall in only the peak or only the off-peak
   bucket (possible with sparse utilization data even when the calendar span
   itself covers the full lookback window), there's nothing to compare
   against - excluded rather than guessed, same principle as every other
   check in this codebase.

5. **Savings estimate scales by the schedule template's off-hours fraction of
   a week (118/168 ~= 70%), derived from the same business-hours constants the
   usage-pattern check uses** (`BUSINESS_HOURS_START_UTC`/`_END_UTC` and
   `BUSINESS_DAYS` from `peak_usage_evaluation.py`), not a separately
   hardcoded number - so the "when the resource would be off" definition used
   for the dollar estimate can't drift out of sync with the "when is
   business hours" definition used for the usage-pattern flag itself. This
   assumes cost is roughly uniform per hour while running, which is stated
   explicitly in the response's `savings_note`, same "approximate, not a
   billing quote" caveat as Tasks 9 and 10.

6. **The business-hours-is-fixed-UTC simplification is surfaced in the
   response itself** (`business_hours_definition` field), not just in
   `results.txt` or a code comment - per the task's explicit "state this
   assumption plainly in the response, don't bury it" instruction.

## One test-authoring bug caught and fixed before running (not a code bug)

While writing test_peak_usage_evaluation.py, the first draft built "peak"
readings across all 14 calendar days (including weekends) at a business-hour
clock time. Since is_business_hours() requires weekday AND time-of-day, the
weekend entries at that same clock time fall into the *off-peak* bucket, not
peak - contaminating the expected off-peak average in three tests with a
mix of my "peak" value and my "off-peak" value, not the clean numbers I'd
calculated by hand. Caught this by working through the exact math before
trusting the assertions (10 weekday peak entries vs 4 contaminated weekend
entries + 14 off-peak entries), not by running and seeing a failure - added
a `_weekday_readings()` helper that skips weekends entirely for the "peak"
stream in the affected tests, which matches how a real business-hours-only
workload actually behaves anyway.

+from dataclasses import dataclass
+from datetime import datetime, timedelta
+from statistics import mean
+
+# v1 simplification, stated explicitly rather than buried: a fixed weekday
+# business-hours window in UTC, not per-resource timezone detection - there's
+# no reliable timezone signal in what Task 2 syncs (no resource-level
+# timezone field), so a single fixed window is used for every resource
+# regardless of its actual region/timezone.
+BUSINESS_HOURS_START_UTC = 8
+BUSINESS_HOURS_END_UTC = 18  # exclusive
+BUSINESS_DAYS = frozenset(range(5))  # Monday=0 .. Friday=4
+
+
+def is_business_hours(timestamp: datetime) -> bool:
+    return timestamp.weekday() in BUSINESS_DAYS and BUSINESS_HOURS_START_UTC <= timestamp.hour < BUSINESS_HOURS_END_UTC
+
+
+@dataclass
+class PeakOffPeakUsageResult:
+    peak_avg_cpu_percent: float | None
+    off_peak_avg_cpu_percent: float | None
+    insufficient_data: bool
+    is_flagged: bool
+    detail: str
+
+
+def evaluate_peak_off_peak_usage(
+    readings: list[tuple[datetime, float]],
+    lookback_days: int,
+    off_peak_ratio_threshold: float,
+) -> PeakOffPeakUsageResult:
+    """Compare average CPU during business hours (weekday 8am-6pm UTC) against
+    nights/weekends, over the trailing `lookback_days` window ending on the
+    most recent reading.
+
+    A genuinely different kind of analysis than `evaluate_cpu_utilization`'s
+    flat average - this buckets by time-of-day/day-of-week first. Flags a
+    resource when off-peak usage is at most `off_peak_ratio_threshold` of
+    peak usage (e.g. 0.5 = off-peak is half of peak or less).
+
+    Same "insufficient data -> exclude, don't guess" principle as every other
+    recommendation check: too little history, or a window that happens to
+    have no readings in one of the two buckets, both return
+    insufficient_data=True rather than a partial/misleading comparison. A
+    peak average of ~0% is also not flagged via this check (division by a
+    near-zero peak isn't a meaningful ratio) - that's an idle-resource
+    situation for the rightsizing check to catch, not a peak/off-peak pattern.
+    """
+    if not readings:
+        return PeakOffPeakUsageResult(None, None, True, False, "No utilization data available.")
+
+    timestamps = [ts for ts, _ in readings]
+    most_recent = max(timestamps)
+    earliest = min(timestamps)
+    span_days = (most_recent.date() - earliest.date()).days + 1
+    if span_days < lookback_days:
+        return PeakOffPeakUsageResult(
+            None, None, True, False, f"Only {span_days} day(s) of history against a {lookback_days}-day window."
+        )
+
+    window_start_date = most_recent.date() - timedelta(days=lookback_days - 1)
+    windowed = [(ts, value) for ts, value in readings if ts.date() >= window_start_date]
+
+    peak_values = [value for ts, value in windowed if is_business_hours(ts)]
+    off_peak_values = [value for ts, value in windowed if not is_business_hours(ts)]
+    if not peak_values or not off_peak_values:
+        return PeakOffPeakUsageResult(
+            None, None, True, False, "Window doesn't contain readings in both the peak and off-peak buckets."
+        )
+
+    peak_avg = mean(peak_values)
+    off_peak_avg = mean(off_peak_values)
+
+    if peak_avg <= 0:
+        return PeakOffPeakUsageResult(
+            peak_avg,
+            off_peak_avg,
+            False,
+            False,
+            "Peak-hours average CPU is ~0%; the peak/off-peak ratio isn't meaningful here.",
+        )
+
+    ratio = off_peak_avg / peak_avg
+    is_flagged = ratio <= off_peak_ratio_threshold
+    comparison = "<=" if is_flagged else ">"
+    detail = (
+        f"peak avg {peak_avg:.2f}%, off-peak avg {off_peak_avg:.2f}% "
+        f"(ratio {ratio:.2f} {comparison} threshold {off_peak_ratio_threshold})"
+    )
+    return PeakOffPeakUsageResult(peak_avg, off_peak_avg, False, is_flagged, detail)

+def _daily_readings(start: datetime, days: int, hour: int, value: float) -> list[tuple[datetime, float]]:
+    return [(start.replace(hour=hour) + timedelta(days=d), value) for d in range(days)]
+
+
+def _weekday_readings(start: datetime, days: int, hour: int, value: float) -> list[tuple[datetime, float]]:
+    """Like _daily_readings, but skips weekends - for building "peak" streams
+    without leaking a weekend reading at a business-hours clock time into the
+    off-peak bucket (weekends are off-peak regardless of hour)."""
+    return [
+        (start.replace(hour=hour) + timedelta(days=d), value)
+        for d in range(days)
+        if (start + timedelta(days=d)).weekday() < 5
+    ]
