# TASK 13 RESULTS - Dashboard: Landing Page (Aggregate Spend + Forecast)

## Two things flagged and resolved before/during the build, not silently guessed on

### 1. The task's premise about /api/v1/forecast was wrong - flagged to Edson directly, resolved with his answer

The task said calling `GET /api/v1/forecast` with no filters "returns both historical
rollups and the forecast." Reading the actual code (`backend/app/services/forecast.py`,
`backend/app/services/forecasting/linear_burn_rate.py`) before writing any frontend
code showed this isn't true: `series` contains only *future* dates
(`most_recent_date+1` through `+horizon_days`), every point using the same flat
`daily_rate` from `LinearBurnRateModel`. `rollups` are sums over those same future
points, not historical spend, despite the name. I checked every GET route in the
backend (forecast, health, the four recommendation endpoints) and confirmed there was
no endpoint anywhere returning historical daily cost data - `/api/v1/cost` had only a
`POST /sync` trigger, nothing to read actuals back out.

This directly blocked a literal scope requirement: the design skill's solid-line-
actual/dashed-line-projected chart treatment. There was no way to build the "solid"
half from real data via the API surface the task scoped ("frontend calls the real
/api/v1/forecast endpoint... not a mock/stub"), and fabricating historical data would
have violated that same instruction plus the design skill's own point about not
overstating a v1 burn-rate guess as real history.

I stopped and asked Edson directly (he was present in the session, not "stepped away"
- see note below on a cross-session message that claimed otherwise) rather than
guessing at a workaround. He chose: **add a small new backend endpoint** so the
frontend can show a real solid-actual/dashed-projected chart, over the alternative of
shipping an all-dashed chart with no historical segment.

**What I built as a result:** `GET /api/v1/cost` (backend/app/api/cost.py), backed by
a new `build_daily_cost_history()` in `backend/app/services/forecast.py` that reuses
the existing `get_daily_costs()` query (same filters, same underlying data as
forecast's aggregate) - returns `{"series": [{"date": ..., "actual_cost": ...}, ...]}`.
This is the historical counterpart to `build_forecast`'s projected series; nothing
about `build_forecast` itself changed.

### 3. A second gap found only once I tried to actually verify the build in a browser: no CORS config

Once the frontend and backend were both built, a real headless-browser load of
`http://localhost:5173` showed a "couldn't reach the backend" error - even though the
same endpoints returned 200 fine via `curl` from the host. Console output showed why:
`Access to fetch at 'http://localhost:8000/...' from origin 'http://localhost:5173'
has been blocked by CORS policy`. `curl` doesn't enforce CORS, so every prior task's
"live check" (all server-side curls) would never have caught this - Task 1's health-
check page never got a real in-browser check either. This isn't a Task-13-specific
bug; it's a structural gap that would have blocked *any* frontend calling *any*
backend endpoint from a browser, so I fixed it rather than working around it or
reporting a false negative on my own build:

- Added `CORSMiddleware` to `backend/app/main.py`, scoped to a new
  `settings.frontend_origin` (default `http://localhost:5173`, the actual Vite dev
  server origin from docker-compose) rather than a wildcard - GET-only, since that's
  all this API currently exposes, and no credentials are involved.
- This is a config change, not a permission/credential/AV-EDR change, so I didn't
  treat it as a CLAUDE.md hard stop - but flagging the reasoning explicitly rather
  than making it silently, per the same "flag rather than guess" instinct as #1 above.

## Design decisions (flagged explicitly)

1. **"Current spend" = trailing 30-day sum of real actual cost data**, not a forecast
   rollup. The task called this "aggregate current spend" and pointed at the forecast
   endpoint for it, but per #1 above that endpoint has no historical data at all - using
   a projected figure and labeling it "current" would have been actively misleading,
   which the design skill itself warns against ("the UI should carry that honesty").
   Trailing-30-day actual spend is the closest honest match to what "current spend"
   normally means in cost-management tooling.

2. **Chart boundary continuity**: `combineSpendSeries()` (frontend/src/lib/) gives the
   *last* actual point a `projected` value equal to itself, so the dashed line starts
   exactly where the solid line ends instead of leaving a gap between "last known day"
   and "first projected day." Pure function, unit-tested directly (3 tests), not
   dependent on Recharts internals.

3. **Empty-state condition uses `forecast.insufficient_data` alone**, not also
   checking `history.series.length === 0` separately - both endpoints derive from the
   exact same unfiltered daily-cost query for the aggregate case, so they're
   necessarily in sync; checking both would be redundant, not more correct.

4. **Testing stack: Vitest + React Testing Library + jsdom.** Task 1 had no testing
   setup to inherit. Vitest was the natural choice given Vite is already the build
   tool (shares config/transform pipeline, no separate Jest+ts-jest+babel setup
   needed); RTL is the standard for behavior-level React component tests over
   implementation-detail testing. Recharts' `ResponsiveContainer` needs
   `ResizeObserver` and non-zero container dimensions that jsdom doesn't provide by
   default - mocked both in `frontend/src/setupTests.ts` rather than avoiding
   ResponsiveContainer or skipping chart-rendering tests.

5. **`frontend/src/vite-env.d.ts` added** - this was actually a pre-existing gap from
   Task 1, not something I introduced: `App.tsx` already used
   `import.meta.env.VITE_API_URL` with no `/// <reference types="vite/client" />`
   anywhere, so `tsc -b` (the first step of `npm run build`) would have failed on
   Task 1's own code too - it seems `npm run build` was never actually run to verify
   Task 1. Fixed as part of getting a clean build for Task 13's own new code.

+import type { CostHistoryPoint, ForecastPoint } from "../api/types";
+
+export interface SpendChartPoint {
+  date: string;
+  actual?: number;
+  projected?: number;
+}
+
+/**
+ * Merges actual daily-cost history with the projected forecast series into a
+ * single chart-ready array. The last actual point also carries the same value
+ * under `projected` so the dashed line starts exactly where the solid line
+ * ends, instead of leaving a visual gap between "last known day" and "first
+ * projected day".
+ */
+export function combineSpendSeries(history: CostHistoryPoint[], forecast: ForecastPoint[]): SpendChartPoint[] {
+  const points: SpendChartPoint[] = history.map((point) => ({ date: point.date, actual: point.actual_cost }));
+
+  if (points.length > 0 && forecast.length > 0) {
+    const last = points[points.length - 1];
+    points[points.length - 1] = { ...last, projected: last.actual };
+  }
+
+  for (const point of forecast) {
+    points.push({ date: point.date, projected: point.projected_cost });
+  }
+
+  return points;
+}
